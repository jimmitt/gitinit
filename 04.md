Branches let two lines of work move independently. Merging joins them again.
Because a branch is only a movable name for a commit, creating one is cheap and
instant.

## Create a focused branch

Start from an up-to-date `main`:

```console
$ git switch main
$ git fetch origin
$ git merge --ff-only origin/main
$ git switch -c feature/mango-salsa
```

The `--ff-only` option updates `main` only when it can move straight forward;
it refuses to invent a merge if local `main` has diverged.

Commit normally on the feature branch:

```console
$ git add salsa.md
$ git commit -m "Add mango salsa recipe"
```

## Fast-forward and three-way merges

If `main` has not changed, merging can simply move its branch name forward:

```console
$ git switch main
$ git merge feature/mango-salsa
```

That is a **fast-forward**. If both branches have new commits, Git performs a
three-way merge using both tips and their best common ancestor. When edits do
not overlap incompatibly, Git combines them automatically and creates a merge
commit.

View the shape of the result:

```console
$ git log --oneline --graph --decorate --all
```

## Resolve a conflict

A conflict means Git needs a human decision, not that the repository is broken.
Start by reading the situation:

```console
$ git status
```

A conflicted text file contains markers like these:

```text
  <<<<<<< HEAD
Add one diced mango.
  =======
Add two diced mangoes.
  >>>>>>> feature/mango-salsa
```

Edit the file to the correct final content and remove all three marker lines.
Then stage and finish the merge:

```console
$ git add salsa.md
$ git diff --check
$ git commit
```

Run the project's tests before committing. The merge result is your code; Git
can identify competing edits, but it cannot decide the recipe's intent.

If you are not ready to resolve the merge:

```console
$ git merge --abort
```

This returns to the pre-merge state when possible. It is easiest and safest to
start merges with a clean working tree.

## Merge the branch you name into the branch you are on

This direction trips up newcomers. In:

```console
$ git switch main
$ git merge feature/mango-salsa
```

`main` is the destination because it is checked out; `feature/mango-salsa` is
the source named to `git merge`. Always run `git status` or `git branch --show-current`
before a merge if you are unsure.

## Merge or rebase?

Merging preserves the existing graph. Rebasing copies commits onto a new base,
creating new commit identifiers and a more linear story:

```console
$ git switch feature/mango-salsa
$ git rebase main
```

Rebase is useful for cleaning up your own unpublished branch. Do not rebase
commits that teammates are already building on unless the team has explicitly
agreed to rewrite that branch. This tutorial defaults to merge because it makes
the collaboration history explicit.

## Reduce painful conflicts

- Keep branches short-lived and focused.
- Fetch often and integrate the shared branch regularly.
- Separate mechanical formatting from behavior changes.
- Avoid mixing unrelated edits in one commit.
- Communicate before two people restructure the same area.
- Let tests and linters check the merged result.

Conflicts become routine when commits are small and the graph is understood.

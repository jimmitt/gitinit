Git is useful even when you work alone. It remembers good states of a project,
shows what changed, and gives experiments a safe home.

## Configure your identity

Each commit records its author. Set your name and email once:

```console
$ git config --global user.name "Your Name"
$ git config --global user.email "you@example.com"
$ git config --global init.defaultBranch main
```

These values are metadata, not login credentials.

## Start a repository

Move to the top of a project and initialize it:

```console
$ cd countdown
$ git init
Initialized empty Git repository in .../countdown/.git/
```

The hidden `.git` directory contains the repository. Your ordinary project
files around it are the working tree. Do not edit `.git` by hand.

Before adding files, create a `.gitignore` for generated files, dependencies,
editor clutter, local configuration, and secrets that should never be tracked:

```gitignore
.env
node_modules/
dist/
*.log
```

Ignoring a file is not a security system. If a secret has already been
committed, remove it from use and rotate it.

## Inspect, stage, and commit

Ask Git what it sees:

```console
$ git status
```

Stage the files for the first snapshot, review the staged change, and commit:

```console
$ git add .
$ git diff --staged
$ git commit -m "Create countdown application"
```

`git add .` is convenient for a small first commit. Later, prefer explicit
paths or `git add -p`, which lets you choose individual change hunks.

After editing `app.js`, the safest everyday sequence is:

```console
$ git status
$ git diff
$ git add app.js
$ git diff --staged
$ git commit -m "Handle countdown completion"
```

`git diff` shows unstaged changes. `git diff --staged` shows exactly what the
next commit will contain. A good commit message finishes the sentence “This
commit will …” and explains one coherent change.

## Add, move, and remove files

Git notices content, but the staging area still determines the next snapshot:

```console
$ git add notes.md
$ git mv old-name.md new-name.md
$ git rm obsolete.md
$ git status
```

`git mv` and `git rm` are conveniences. Moving or deleting with your normal file
tools and then running `git add -A` records the same resulting snapshot. Git
detects renames by similarity when it compares commits.

## Read history

```console
$ git log --oneline --decorate --graph
8b7210a (HEAD -> main) Handle countdown completion
45ed21c Create countdown application
```

The short hexadecimal strings identify commits. `HEAD -> main` says that you
are on `main` and it points to the newest commit.

Useful ways to inspect history include:

```console
$ git show 45ed21c
$ git log -- app.js
$ git blame app.js
```

`git show` displays a commit and its patch. `git log -- path` follows a file's
history. `git blame` shows the last commit responsible for each line; use it as
a route to context, not as a route to blame a person.

## The daily local loop

1. Edit files.
2. Run `git status` and `git diff`.
3. Stage a coherent change with `git add`.
4. Review it with `git diff --staged`.
5. Commit it with a useful message.

That loop is Git's foundation. Sharing those commits is the next layer.

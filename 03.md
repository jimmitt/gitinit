Git offers several kinds of “undo” because mistakes happen in different places.
Before changing anything, run `git status`. Then identify whether the mistake is
in the working tree, the staging area, a local commit, or published history.

## Discard an unstaged edit

To replace one working file with its staged version:

```console
$ git diff -- guacamole.md
$ git restore guacamole.md
```

This discards uncommitted content and is not normally recoverable. To remove all
unstaged tracked-file edits, use `git restore .` only after reviewing the scope.

Untracked files are different. `git clean -n` previews what Git could remove;
do not run the destructive form casually.

## Unstage without losing the edit

If you staged the wrong file:

```console
$ git restore --staged secrets-of-salsa.md
```

The file remains edited in your working tree; it simply leaves the proposed
commit. Use `git status` to confirm.

## Correct the most recent local commit

If the latest commit has not been shared, stage the correction and amend it:

```console
$ git add forgotten-test.js
$ git commit --amend
```

Amending creates a replacement commit with a new identifier. Avoid amending a
published commit unless collaborators expect the branch to be rewritten.

To keep the changes but remove the latest local commit:

```console
$ git reset --soft HEAD~1
```

The branch moves back one commit and the changes stay staged. `git reset` moves
branch history, so it is best reserved for unpublished work. The `--hard` mode
also discards working files and should never be a reflex.

## Undo a published commit

Shared history should usually grow forward. `git revert` creates a new commit
whose patch reverses an older one:

```console
$ git show 8b7210a
$ git revert 8b7210a
```

That preserves the original event and the later decision to undo it. If the
original change overlaps newer work, resolve the conflicts, stage the result,
and continue the revert.

Reverting a merge requires choosing which parent represents the mainline. Do
not guess: inspect the graph and coordinate with the team first.

## Put experiments on branches

Create a branch before a risky idea:

```console
$ git switch -c experiment/new-sauce
```

If it works, merge it or open a pull request. If it fails, switch away and
delete the branch after making sure nothing valuable exists only there:

```console
$ git switch main
$ git branch -d experiment/new-sauce
```

Git refuses `-d` when commits are unmerged. Capital `-D` overrides that safety
check, so use it only after inspection.

## Recover a commit with the reflog

Even after a reset or deleted branch, a recently referenced commit may still be
visible in your local reference log:

```console
$ git reflog
$ git branch recovered-work a1b2c3d
```

The reflog is local and expires over time. It is an emergency net, not a backup
strategy.

## Choose the undo tool by location

| Problem | Usual tool |
| --- | --- |
| Unstaged tracked-file edit | `git restore <path>` |
| Staged by mistake | `git restore --staged <path>` |
| Latest unpublished commit needs correction | `git commit --amend` |
| Unpublished branch should move backward | `git reset` |
| Published commit should be undone safely | `git revert <commit>` |
| Lost local branch or commit | `git reflog` |

Pause before commands that discard files or move branch names. Git is excellent
at retaining committed objects; it cannot rescue work it never recorded.

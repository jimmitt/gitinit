Git does not prescribe one server or branching policy. It gives you commits,
references, and ways to exchange them. Your team supplies the workflow.

## Commits form a graph

Most commits point to one parent. A merge commit usually points to two. Branches
and tags are readable names that ultimately point into this graph.

```text
o---o---o  main
     \
      o---o  feature
```

The commits are the durable history. Branch names are meant to move; tags are
normally meant to stay put.

## Branches model ongoing lines of work

Common patterns include:

- a protected `main` branch that should always pass checks
- short-lived feature and fix branches reviewed through pull requests
- a release branch maintained while newer development continues

You do not need a branch for every environment or person. Add long-lived
branches only when they express a real, maintained line of development.

For a production fix that must also reach current development:

```console
$ git switch release/1.x
$ git switch -c fix/login-timeout
# edit, test, commit, and merge through review
```

After the fix is accepted on the release line, merge that commit or branch into
`main`. For a small self-contained fix, a team may instead apply the commit with
`git cherry-pick <commit>`. Cherry-picking creates a new commit, so record why
the duplication was needed.

## Tags name releases

An annotated tag stores a name, message, tagger, and target:

```console
$ git tag -a v1.1.0 -m "Release 1.1.0"
$ git show v1.1.0
$ git push origin v1.1.0
```

Tags are not pushed by every ordinary `git push`; publish the intended tag
explicitly. Treat a published release tag as immutable. If it identifies the
wrong commit, coordinate a correction instead of silently moving it.

To inspect an old release without moving a branch:

```console
$ git switch --detach v1.1.0
```

Create a branch before committing from this detached state.

## One repository, several remotes

A clone may pull from the canonical project and push to your fork:

```console
$ git remote rename origin upstream
$ git remote add origin https://example.com/you/recipes.git
$ git fetch --all --prune
```

Names such as `origin` and `upstream` are conventions. Check their URLs before
pushing with `git remote -v`.

## Bare repositories live on servers

A normal repository has a working tree and a `.git` directory. A **bare**
repository has the Git database and references but no checked-out files:

```console
$ git init --bare recipes.git
```

Bare repositories are suitable as push targets. In practice, hosting services
provide authentication, review, protected branches, issue tracking, and CI on
top of that storage.

## Worktrees provide another checkout

You rarely need to clone a local repository just to work on two branches at
once. A linked worktree shares the object database while providing another
working directory:

```console
$ git worktree add ../recipes-release release/1.x
$ git worktree list
```

This is handy for maintaining a release while development files remain open in
your main working tree.

## Choose a workflow, then protect it

A small team can succeed with `main`, short feature branches, pull requests,
and tagged releases. Larger projects may add release branches, forks, or a
merge queue. Whatever the shape, document:

- which branches are long-lived and who may update them
- whether integration uses merge commits, squash merges, or rebases
- which checks must pass before merging
- how releases are tagged and deployed
- whether force-pushes are allowed anywhere

You now have the full model: snapshots become commits; branch and tag names point
into the commit graph; remotes exchange objects and references; merging combines
histories. Every advanced Git workflow is built from those pieces.

Teams usually meet through a hosted repository on GitHub, GitLab, Bitbucket, or
an internal server. The server is important for coordination, review, access
control, automation, and backups—but it is still another Git repository.

## Clone the project

```console
$ git clone https://example.com/team/recipes.git
$ cd recipes
$ git remote -v
origin  https://example.com/team/recipes.git (fetch)
origin  https://example.com/team/recipes.git (push)
```

Cloning downloads the history, creates a working tree, names the source
`origin`, and configures the initial local branch to track its counterpart.

## Understand tracking branches

Suppose you work on local `main`. Git may configure it to track `origin/main`.
These are different names:

- `main` moves when you make or integrate commits locally.
- `origin/main` is your local record of the remote's `main` at the last fetch.

See the relationship with:

```console
$ git branch -vv
* main 8b7210a [origin/main] Handle countdown completion
```

## Fetch before you integrate

`git fetch origin` downloads new Git objects and updates remote-tracking
branches. It does not edit your working files:

```console
$ git fetch origin
$ git log --oneline --graph --decorate --all
$ git diff main..origin/main
```

When you are ready, merge the fetched work:

```console
$ git switch main
$ git merge origin/main
```

`git pull` is shorthand for fetching and then integrating into the current
branch. Because it performs two actions, beginners often learn more by fetching
and inspecting first. Teams should agree whether pulls merge or rebase; this
tutorial uses merges unless it explicitly says otherwise.

## Work on a branch

Avoid building every change directly on `main`:

```console
$ git switch -c improve-guacamole
# edit and test
$ git add guacamole.md
$ git commit -m "Clarify how to choose ripe avocados"
```

Publish the new branch and establish its upstream:

```console
$ git push -u origin improve-guacamole
```

Later pushes from that branch can be just `git push`. On a hosting service, you
would normally open a pull request or merge request so teammates and automated
checks can review the change before it reaches `main`.

## When a push is rejected

Git normally rejects a push if updating the remote branch would discard commits
that are already there. Fetch and look before acting:

```console
$ git fetch origin
$ git log --oneline --left-right HEAD...origin/main
```

If you are updating `main`, integrate the remote work, test, then push:

```console
$ git switch main
$ git merge origin/main
$ git push origin main
```

Do not reach automatically for `--force`. On a shared branch, rewriting the
remote branch can erase other people's reachable work. If a team intentionally
allows rewritten feature branches, `--force-with-lease` adds a safety check,
but it still needs care and agreement.

## A healthy collaboration rhythm

1. Fetch and inspect the current shared work.
2. Create a short-lived branch.
3. Make small, tested commits.
4. Push the branch and request review.
5. Incorporate feedback and let checks run.
6. Merge through the team's agreed process.
7. Delete the finished feature branch when it is no longer needed.

Git exchanges commits; hosting platforms add the conversation and guardrails
around them.
